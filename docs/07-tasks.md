## Этап 3. Теги, категории, иконки

- [x] Схема тегов: `TagCategory`, `Tag`, `EventTag`, enum `TagColor` (миграции применены).
- [x] Палитра цветов тегов: enum `TagColor` в схеме, токены `--color-tag-*` и `--color-on-tag-*` для обеих тем.
- [x] API категорий (`features/calendar/tag-categories`): список с вложенными тегами, создание с лимитом и `sortOrder` в конец, переименование, переключение `multiple` с 409 при конфликте, удаление каскадом. Проверено вручную по HTTP, 37 сценариев: роли (VIEWER только читает, посторонний получает 404), валидация, порядок, лимит, конфликт `multiple`, каскад.
- [x] Исправить 500 на `null`: `multiple` в `TagCategoryCreateDto` и `color` в `TagCreateDto` стали обязательными (без `@IsOptional()`), значение всегда шлёт форма. `null` теперь даёт 400 и в создании, и в изменении (`PartialType` с `skipNullProperties: false` пропускает только отсутствующее поле).
- [x] API тегов (`features/calendar/tags`): создание в категории с лимитом `MAX_TAGS_PER_CATEGORY` и `sortOrder` в конец (доступ через `TagCategoryService.getAuthorizedTagCategory`), изменение, удаление (204, связи с событиями каскадом). Проверено вручную по HTTP, 35 сценариев: роли, валидация цвета и имени, `null` даёт 400, порядок, лимит, каскад.
- [x] Назначение тегов событию (бэкенд): `POST` и `DELETE events/:id/tags/:tagId`, по одному тегу на запрос, ответ: событие целиком с актуальными `tagIds`. Доступ EDITOR, тег должен быть из календаря события. Для категории с `multiple = false` `POST` в одной транзакции снимает другой тег этой категории. Повторы безопасны (`skipDuplicates`, `deleteMany`). В `EventDto` поле `tagIds: string[]`. Проверено вручную по HTTP вместе с пустым названием, 34 сценария: добавление и повтор, радиокнопки при `multiple = false`, `tagIds` в списке и после `PATCH`, чужой и несуществующий тег (404), роли, снятие и повтор, 409 при переключении категории через настоящие связи, каскад при удалении тега и события.
- [x] Пустое название события (бэкенд): `title` в `EventCreateDto` допускает пустую строку (`Trim` и `IsString` вместо `IsNotBlank`, как у календаря), чтобы событие создавалось сразу по клику. Пробелы обрезаются до пустой строки, `null`, число и отсутствующее поле дают 400. Плейсхолдер вместо пустого названия на карточке и в диалоге делается вместе с автосохранением на фронте.
- [ ] Автосохранение диалога события (фронт): клик по календарю сразу создаёт событие с пустым названием, как в Notion. Каждое изменение уходит отдельным `PATCH` только с изменённым полем: название с debounce и при потере фокуса (при закрытии диалога отложенное сохранение отправляется сразу), остальные поля сразу. Запросы одного события идут по очереди (`concatMap`), ответ сервера заменяет событие локально. Ошибка видна у поля, значение откатывается. Кнопок «Сохранить» и «Отмена» нет, только «Закрыть».
- [ ] Выбор времени (фронт): варианты с шагом 15 минут и ручной ввод произвольного времени. Конец всегда позже начала: минимум начало + 15 минут. При сдвиге начала конец сдвигается на ту же величину, длительность сохраняется.

## После этапа 3. Ручная сортировка событий внутри дня

Пока не делаем. Решения (по схеме Todoist):

- События со временем стоят выше и идут по времени, ручной порядок на них не действует. Многодневные полосы FullCalendar ставит выше однодневных.
- События на весь день идут в ручном порядке.
- Новое событие на весь день встаёт в конец дня.
- При переносе на другой день событие встаёт в конец этого дня.
- Выполненное событие остаётся на своём месте.
- Порядок хранится в `Event.position` (`Float`), при переносе внутри дня берётся среднее между соседями.

- [ ] Поле `position` у `Event`, миграция, DTO.
- [ ] `eventOrder` в FullCalendar: сначала ручная позиция, потом порядок по умолчанию.
- [ ] Перенос внутри дня: `eventDragStop` и расчёт позиции по соседним событиям.
- [ ] Позиция в конце дня при создании и при переносе на другой день.
