# Гайд: автосохранение диалога события

Пособие для задачи «Автосохранение диалога события (фронт)» из этапа 3 в `07-tasks.md`. Код дан каркасами: сигнатуры и структура готовы, а то, что пишешь ты, помечено `// TODO` с целью и критерием. Подсказка дана только для API, которого в проекте ещё не было (`toObservable`, `debounce`, `timer`, `concatMap`, `beforeClosed`). Готового кода в TODO нет.

**Что уже сделано.** Клик по дате сразу создаёт событие на весь день с пустым названием и открывает диалог в режиме редактирования. Из диалога убраны `save()`, подтверждение при закрытии и обязательность названия. `EventDialogResult` теперь только `{ action: 'delete' } | undefined`. Пустое название показывается плейсхолдером `event.untitled` в поле и на карточке. **Пока шаги ниже не сделаны, изменения в диалоге никуда не сохраняются.**

## Что должно получиться

Диалог открыт → пользователь меняет поле → уходит `PATCH` только с этим полем → ответ сервера обновляет карточку в календаре, а форма остаётся как есть.

- Название и описание сохраняются после паузы в наборе, а также сразу при потере фокуса, Enter (только название) и закрытии.
- «Выполнено» и даты сохраняются сразу.
- Запросы одного события идут строго по очереди.
- При ошибке поле откатывается к последнему значению с сервера, под ним появляется текст ошибки.

## Шаг 2. Состояние диалога

```ts
// STATE
private readonly saved = signal(this.data.event);
private readonly flushText$ = new Subject<void>();
readonly saveError = signal<AutosaveField | null>(null);
```

- `saved`: последнее событие, которое вернул сервер. Ответы пишутся только сюда, **в `model` никогда**: иначе пропадут символы, набранные, пока шёл запрос.
- `flushText$`: заставляет отложенный текст уйти сразу (`blur`, Enter).
- `saveError`: у какого поля показать ошибку. `AutosaveField = 'title' | 'description' | 'completed' | 'dates'`.

```ts

constructor() {
  this.autosave();

```

**Каждый источник:**

1. Сигнал значения поля превращается в поток. Для текста `computed(() => this.model().title)`, для дат `datesPayload`.
2. Первым оператором `takeUntil(closed$)`.
3. Только для текста: отложенная отправка, которую можно протолкнуть через `flushText$`.
4. Значение превращается в частичный `PATCH` (`{ title }`, `{ completed }`, объект дат) вместе с именем поля для ошибки.
5. Отбросить всё, что совпадает с `saved()`. Это заменяет `skip(1)` и `distinctUntilChanged`: первое значение равно серверному, «напечатал и стёр» не шлёт `PATCH`, откат не уходит повторно.

Критерий: открыли и закрыли диалог без изменений, ни одного запроса.

**Общий хвост после `merge`:** отправлять каждое изменение через `data.update` строго по очереди. Успех: ответ в `saved`, сбросить `saveError`. Ошибка: обработчик отката из шага 5, вернуть `EMPTY`, чтобы очередь не оборвалась.

Критерий: быстро изменили название, потом «выполнено», в Network два запроса, второй начался после ответа на первый.

**Подсказки по новым API:**

- `toObservable` (`@angular/core/rxjs-interop`): превращает сигнал в поток. Работает только в injection context, поэтому вызывается из конструктора. Сразу отдаёт текущее значение, а при уничтожении компонента завершается.
- `debounce`: как `debounceTime`, но паузу задаёт функция, которая возвращает поток; значение уходит, когда этот поток что-то отдаст. Важно: если источник завершился, а значение ещё ждёт, `debounce` отдаёт его сразу. На этом держится сохранение при закрытии.
- `timer(ms)`: поток, который отдаёт одно значение через `ms`. Вместе с `flushText$` через `merge` получается «через паузу или сразу по сигналу, что раньше».
- `concatMap`: ставит внутренние запросы в очередь, следующий начинается, когда закончился предыдущий. `switchMap` здесь нельзя: он отменил бы уже отправленный `PATCH` другого поля.
- `dialogRef.beforeClosed()`: отдаёт значение в момент начала закрытия, до уничтожения компонента.

**Две ловушки:**

1. **Не ставить `takeUntilDestroyed()` после `concatMap`.** Закрытие отменит последний запрос, а в нём часто лежит отложенное название. Поток завершится сам: источники закончатся на `closed$`, `concatMap` отправит остаток очереди и завершится.
2. **`takeUntil(closed$)` до `debounce`, не после.** Иначе отложенное значение отбросится, а не отправится.

## Шаг 6. Шаблон и переводы

- У названия `(blur)` и `(keydown.enter)` вызывают `flushText$.next()`. У описания только `(blur)`: Enter в `textarea` это перенос строки.
- Под полем, которое совпадает с `saveError()`, вывести `<mat-error>` с новым ключом, например `event.errors.saveFailed`, во всех трёх языках (`ru`, `en`, `es`). Для дат это поле диапазона, для «выполнено» строка рядом с чекбоксом.
- `cancel()` переименовать в `close()`: это больше не отмена.

## Проверка вручную (Network в DevTools)

1. Печатаешь название: один запрос после паузы, а не на каждую букву.
2. Печатаешь и сразу закрываешь крестиком: запрос всё равно уходит, на карточке новое название.
3. Печатаешь и уводишь фокус: запрос сразу, без паузы.
4. «Добавить время» и «Убрать время»: один `PATCH` с тремя полями.
5. Диапазон дат: после первого клика может уйти `PATCH` с одним днём, после второго с диапазоном. Это ожидаемо, порядок сохранится.
6. Ошибка: в DevTools режим Offline, меняешь поле, оно откатывается, под ним текст ошибки.
7. Открыл и закрыл без изменений: ни одного запроса.
8. Для `VIEWER` поток не создаётся, запросов нет.

На ревью в первую очередь: где стоят `takeUntil` и `debounce` относительно друг друга и что ответ сервера не попадает в `model`.
