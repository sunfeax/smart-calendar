# Бэкенд и авторизация

## Структура Nest-проекта

Модули: `auth`, `session`, `users` и в `features/calendar` модули `calendars`, `events`, `tag-categories`, `tags`, `members`, `invites`. Позже: `ai`.

- `auth`: вход через Google, logout, `/auth/me`, глобальный guard. Сам сессии не хранит, вызывает `session`.
- `session`: создание, поиск по хешу токена, продление, удаление и очистка просроченных. Отдельно от `auth`, потому что его используют и guard, и вход, а позже экран активных сессий.

Общие части: сервис доступа к календарям (проверка членства и ролей), фильтры ошибок, DTO с валидацией.

## API (эскиз)

Все пути под `/api`.

**Авторизация**

- `POST /auth/google`: принимает ID token, ставит cookie сессии.
- `POST /auth/logout`
- `GET /auth/me`

**Календари**

- `GET /calendars`, `POST /calendars`, `PATCH /calendars/:id`, `DELETE /calendars/:id`
- `GET /calendars/:id/members`: участники с ролями.
- `DELETE /calendars/:id/members/:userId`: удалить участника или выйти самому (свой `userId`).
- `GET /calendars/:id/invites`: активные ссылки (без токенов, с `createdById`, чтобы клиент знал, кто может отозвать).
- `POST /calendars/:id/invites` `{ role }`: создать ссылку, токен приходит один раз в ответе.
- `DELETE /invites/:id`: отозвать ссылку.
- `POST /invites/accept` `{ token }`: принять приглашение, ответ: календарь.

**События**

- `GET /calendars/:id/events?from=&to=`: одиночные события и развёрнутые повторения серий за диапазон. У повторения `id` серии и `originalStart`, у одиночного события `originalStart = null`.
- `POST /calendars/:id/events`
- `PATCH /events/:id`, `DELETE /events/:id`. Для повторения серии query `scope` (`this`, `following`, `all`) и `originalStart`; без `scope` запрос меняет саму запись (одиночное событие или серию целиком). `this` создаёт или обновляет `EventException`, `following` делит серию, `all` сдвигает всю серию на ту же разницу в настенном времени её пояса.
- Ответ события содержит `tagIds: string[]`. Имена и цвета клиент берёт из списка категорий календаря.
- Архив (EDITOR): `DELETE /events/:id` переносит в архив; `GET /calendars/:id/events/archived` (последние 100); `POST /events/:id/restore` возвращает из архива или с `scope=this&originalStart=` снимает отмену одного повторения; `DELETE /events/:id/archived` удаляет навсегда, только архивное.
- Теги события по одному: `POST /events/:id/tags/:tagId`, `DELETE /events/:id/tags/:tagId`, оба возвращают событие целиком.
- Поиск: `GET /calendars/:id/events/search?q=` (от 2 до 100 символов, VIEWER): без учёта регистра по названию, описанию и имени тега, без архивных, до 50 событий. У серии возвращается ближайшее будущее повторение, у закончившейся последнее.

**Теги**

- Категории: `GET` и `POST /calendars/:calendarId/tag-categories` (список с вложенными тегами), `PATCH` и `DELETE /tag-categories/:id`.
- Теги: `POST /tag-categories/:categoryId/tags`, `PATCH` и `DELETE /tags/:id`. Отдельного списка тегов нет, они приходят в списке категорий.

**Прочее**

- Экспорт JSON и ICS (план): `GET /calendars/:id/export?format=json|ics`. XLSX собирается на клиенте.

API описывается через Swagger, из него генерируется клиент для Angular.

## Вход через Google

1. Фронтенд показывает кнопку Google Identity Services и получает ID token (`credential`).
2. Отправляет его на `POST /auth/google`.
3. Бэкенд проверяет токен через `google-auth-library` (подпись, срок, `aud` = наш Client ID).
4. Находит пользователя по `googleId` (поле `sub`) или создаёт нового. Email и имя обновляются при каждом входе.
5. При первом входе создаётся личный календарь.
6. Бэкенд выдаёт сессию в httpOnly-cookie (`Secure`, `SameSite=Lax`).

Сессия хранится в таблице `Session` (в БД хеш токена), 30 дней со скользящим продлением. Refresh-токены не нужны. Схема и поля: `03-data-model.md`.

### Настройка Google

- Проект в Google Cloud Console, OAuth Client ID (тип «Web»).
- В режиме Testing входят только добавленные тестовые пользователи (до 100). Для закрытой беты этого достаточно.
- Публичный запуск: режим Production, домен, политика конфиденциальности, проверка бренда. С базовыми scope полная проверка не нужна.
- Локально: `http://localhost` и `http://localhost:4200` в разрешённых источниках (Google требует оба). Redirect URI не нужен. Для прода добавить домен.

## Безопасность (чек-лист)

- Каждый запрос проверяет членство в календаре и роль (единый сервис доступа).
- DTO с валидацией на всех входах, лимиты длины полей.
- Иконка по ссылке: только `https://`, ограничение длины, на клиенте `referrerpolicy="no-referrer"`.
- Лимиты запросов (`@nestjs/throttler`), `helmet`.
- Один домен для фронтенда и API: меньше проблем с cookie и CORS. CSRF: `SameSite=Lax`, JSON-запросы. Если появится кросс-доменная схема, добавить CSRF-токен.
- Секреты только в переменных окружения.
- Логи без токенов и персональных данных.

## ИИ-агент (позже)

Подход: сначала **tool calling**, RAG не нужен, пока нет неструктурированных заметок.

- Агент получает функции вроде `list_events`, `create_event`, `update_event` и сам решает, что вызвать.
- Агент работает от имени пользователя и видит только его календари (те же проверки доступа).
- Разрушительные действия (удаление, массовые изменения) только с подтверждением в интерфейсе.
- Тексты событий и заметок попадают в промпт, значит это недоверенные данные (риск prompt injection). Нельзя выполнять инструкции из них.
- Лимиты на число запросов и расходы на LLM.
- Ключ API LLM только на сервере.
- RAG: если появятся заметки и документы, добавить `pgvector` в тот же Postgres.
